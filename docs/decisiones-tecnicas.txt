E-MEDICAPP — decisiones de implementación del MVP
9 de octubre de 2026

Autoridad actual: CASOS DE USO - E-MEDICAPP.pdf de QA y respuestas posteriores
del dueño. El PDF V3 completa sólo los puntos compatibles no especificados.
El relevamiento integral
sirve como catálogo de requisitos; las 88 tablas no son una migración inicial.

Decisiones del usuario: circuito completo con integración progresiva delegada;
panel configurable con flujos definidos en código; uso inicial en PC, con
posibilidad de despliegue y acceso remoto.

Java 25 LTS (Temurin), Spring Boot 4.1.1, Maven Wrapper, PostgreSQL 18.6 y Flyway.
React 19.3, TypeScript 6.0 estricto, Vite 8, React Router, TanStack Query,
React Hook Form/Zod y Material UI Core. TypeScript 6 se elige para simplificar
compatibilidad de herramientas; TypeScript 7 existe, pero su 7.0 no expone API
para herramientas que acceden al compilador. Se revisará la transición al
incorporar una versión con compatibilidad probada, sin instalar dos compiladores.

Un backend, una base y un frontend. En uso diario el backend sirve el frontend
compilado bajo un mismo origen. Vite se usa en desarrollo. Node 24 LTS es
herramienta de construcción, no otro servidor de negocio.

Paquetes por función, servicios transaccionales y repositorios con JdbcClient.
DTO records, composición e inyección por constructor. Las interfaces se agregan
cuando existe una frontera con implementaciones distintas. SQL parametrizado.
No motores genéricos de flujos, CRUD universal, CQRS ni event sourcing.
La claridad de estados, transacciones, permisos y cantidades prima sobre
reducir artificialmente el número de archivos.

Configuración: catálogos, precios, stock, farmacias/cadenas/sucursales, horarios,
zonas, capacidades, miembros, planes, suscripciones y tiempos operativos.
Cambios prospectivos y auditados; presupuesto aceptado e historial financiero
se preservan. Las correcciones tienen versión o acción compensatoria.

Extensión QA: confirmación de correo y recuperación mediante tokens de un solo
uso; SMTP configurable después mediante DPAPI, sin autoaprobar un registro.
Reservas al emitir presupuesto, nota por compra, sustitución consentida antes
de presupuesto nuevo, cobros por importe/moneda real, notas fiscales, controles
independientes para cancelación/despacho/reintegro de alto valor, custodia y un
reintento coordinado. Reposiciones enlazadas conservan stock/Rx e historia
originales y usan un nuevo circuito operativo sin cargo.
Se agregan servicios y tablas específicos de estas obligaciones; no se crea
una infraestructura genérica ni se reemplazan transacciones por eventos.

Modelo implementado: 42 tablas de negocio y migraciones V1-V13. El SQL
consolidado conserva las fuentes en orden; Flyway aplica las migraciones del
backend. Los medios de pago declarados se conservan por cobro, sin completar
datos ausentes de pagos históricos. Una falla de emisión fiscal se registra
con evidencia operativa y genera una alerta comercial para administración;
adjuntar la factura válida la resuelve conservando los intentos.

DEMO usa datos sintéticos y marca el entorno. MANUAL requiere usuarios propios,
otra base, condiciones verificadas y comprobaciones externas documentadas.
Stock, receta, cobertura, cobro y factura manuales indican fuente y responsable.
Un archivo de comprobante no confirma por sí solo un cobro. No se simulan
resultados de proveedores oficiales en una operación real.

Sesión de servidor, cookies HttpOnly, CSRF y HTTPS para despliegue remoto.
Los archivos clínicos son privados y descargables por actores autorizados.
No se guardan sesiones en localStorage. Credenciales y datos quedan fuera de Git.
El arranque local usa loopback; no cambia firewall ni expone servicios.

Pruebas necesarias: autorización por recurso/sucursal, presupuesto versionado,
última unidad concurrente, reintentos y doble aceptación, pagos divididos,
reintegro sin duplicación, conservación de datos y flujo por distintos perfiles.
PostgreSQL real aislado para integración; no sustitución por H2.
