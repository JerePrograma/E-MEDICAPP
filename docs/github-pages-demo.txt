E-MEDICAPP - DOMINIO SCALARIS + GITHUB PAGES + BACKEND EN ESTA PC
Actualizado el 21 de octubre de 2026

DIRECCIONES
Repositorio: https://github.com/JerePrograma/E-MEDICAPP
Frontend para compartir: https://scalaris.com.ar/e-medicapp/
Publicacion de origen: https://jereprograma.github.io/E-MEDICAPP/
Backend local: http://127.0.0.1:8082
Base propia: 127.0.0.1:5544 en esta PC (el puerto persistido se lee de .runtime/local-db.json).

PRESENTAR LA DEMO
1. Abrir AbrirDemoPages.cmd desde la carpeta del proyecto.
2. Esperar las confirmaciones del backend HTTPS y de la conexion publicada.
   Compartir https://scalaris.com.ar/e-medicapp/. La direccion normal
   tambien queda guardada en .runtime/demo-pages.json, campo connectionUrl.
   Los usuarios no necesitan agregar parametros ni configurar el servidor.
3. Ingresar con comprador@demo.invalid y DemoMedicapp2026! o elegir un perfil
   de demostracion. Otros perfiles: farmacia@demo.invalid,
   farmaceutico@demo.invalid, farmaceutico2@demo.invalid, cadete@demo.invalid,
   adminfarmacia@demo.invalid y admin@demo.invalid, con la misma contrasena DEMO.
4. Seguir docs/guion-demostracion.txt. Los documentos simulados para adjuntar se
   encuentran en frontend/tests/fixtures.
5. Al finalizar abrir DetenerDemoPages.cmd. Conserva la base y los documentos.

La PC debe permanecer encendida, sin suspension y conectada a Internet.
Cloudflare proporciona un tunel HTTPS temporal sin configurar el router.
La URL trycloudflare.com cambia al reiniciar el tunel. La direccion que se
comparte de Scalaris permanece estable.
Los visitantes consultan exclusivamente scalaris.com.ar/e-medicapp/api/.
Cloudflare resuelve el tunel en el servidor: el navegador no consulta el DNS
de trycloudflare.com ni conserva una direccion temporal dentro de la aplicacion.
El dominio del tunel puede tardar unos segundos en propagarse. El acceso espera
hasta 90 segundos y solo confirma disponibilidad cuando recibe respuesta HTTPS.
AbrirDemoPages.cmd actualiza VITE_API_BASE_URL y solicita publicar Pages cuando
la configuracion publicada no coincide con el tunel actual. Necesita GitHub CLI
con acceso al repositorio. Espera hasta tres minutos a que deployment.json confirme
el commit remoto y el servidor nuevo antes de mostrar el enlace para compartir. Si falla la
publicacion, el backend se conserva activo y el acceso informa que sigue pendiente;
no utiliza una direccion ingresada por el usuario como alternativa.
Para repetir la sincronizacion ejecutar scripts/Sync-DemoPages.ps1 -Wait.
El parametro -Force vuelve a solicitar la publicacion. Start-DemoPages.ps1
sincroniza de forma predeterminada, tambien al reutilizar una demo ya iniciada.

La web publicada utiliza exclusivamente su servidor configurado. Ignora cualquier
servidor guardado en el navegador y elimina ?api=... de enlaces antiguos conservando
los demas parametros y la pantalla. No muestra Conexion, Cambiar servidor ni un
campo para editar la direccion. Una falla ofrece reintentar; una configuracion
invalida no habilita un servidor alternativo. La edicion manual queda limitada al
acceso local de desarrollo, cuando no hay servidor fijado en la compilacion.
El acceso publico a la API es estable aun cuando cambia el tunel interno.
La disponibilidad del backend sigue dependiendo de esta PC y del tunel activo.

El inicio carga automaticamente el escenario ficticio si la base DEMO es nueva:
personas y roles, farmacias de Mendoza, catalogo, precios, existencias, lotes y
documentos de capacidades. No requiere importar datos a mano. Los cambios que
se realicen durante la presentacion quedan guardados para la proxima sesion.
El DEMO no envia correo real, aun si Windows tiene un proveedor SMTP configurado.
El alta/recuperacion de cuentas necesita proveedor en MANUAL; para la demo usar
las cuentas ya habilitadas. No usar datos reales en esta demostracion publica.

PUBLICAR EL FRONTEND EN GITHUB PAGES Y SCALARIS
El flujo .github/workflows/pages.yml compila y prueba frontend/ con Node.js 24.
Solo sube frontend/dist; no sube Java, PostgreSQL, .runtime ni documentos privados.
Se ejecuta al actualizar frontend/ en main o desde Actions -> Run workflow.
En el repositorio, Settings -> Pages -> Build and deployment -> Source debe estar
en GitHub Actions. Al completar el flujo aparece la URL del sitio.

La ruta Vite es ./ para Pages y / para el JAR local. Los recursos relativos
permiten servir la misma compilacion en /E-MEDICAPP/ y /e-medicapp/. Las rutas de
navegacion usan # para que recargar o compartir una pantalla no produzca 404.
La variable de repositorio VITE_API_BASE_URL define el tunel interno HTTPS autorizado.
Con el backend temporal, AbrirDemoPages.cmd la sincroniza cuando cambia el tunel.
El flujo valida esa direccion antes de compilar y registra el servidor y el commit
en deployment.json; publicApiBaseUrl registra https://scalaris.com.ar/e-medicapp.
El frontend web y Android se compilan con esa direccion estable, no con el tunel.
No se publica una web de Pages sin configuracion. Los usuarios
no pueden reemplazar la conexion mediante el enlace o los ajustes del navegador.
Para un despliegue permanente corresponde utilizar un backend con dominio estable.
Los valores VITE_* son publicos y nunca deben contener credenciales.
La autenticacion y los permisos siguen siendo responsabilidad del backend.

El dominio scalaris.com.ar ya pertenece al sitio Scalaris de Cloudflare Pages.
El Worker propio emedicapp-public, definido en deployment/cloudflare/wrangler.jsonc,
intercepta exclusivamente /e-medicapp y /e-medicapp/*. La funcion anterior de Pages
queda como publicacion estatica de respaldo; no es necesario modificar ese proyecto.
GET y HEAD estaticos consultan GitHub Pages sin reenviar credenciales. /api/ consulta
el tunel indicado por deployment.json exclusivamente desde Cloudflare. Conserva
X-Auth-Session, CSRF, idempotencia, archivos y permisos del backend; no reenvia
cookies del sitio Scalaris ni guarda respuestas de API en cache. Admite los origenes
Scalaris, GitHub Pages y Android (https://localhost), sin ampliar permisos de cuentas.
La portada y deployment.json se consultan sin cache, incluyendo el cache del origen.
/e-medicapp redirige a /e-medicapp/ conservando parametros. Las demas rutas de
Scalaris siguen sirviendo sus archivos estaticos habituales.
Cada nueva publicacion de GitHub se refleja en Scalaris sin copiar archivos ni
republicar el sitio corporativo. El enlace anterior de GitHub sigue disponible.
Para modificar el Worker: ejecutar node --test deployment/cloudflare/*.test.mjs y
publicar con wrangler deploy --config deployment/cloudflare/wrangler.jsonc desde
la cuenta Cloudflare autorizada. La configuracion fija el nombre y las dos rutas
del recurso propio. No requiere secretos en GitHub ni cambios en la base.
Sync-DemoPages.ps1 confirma tambien /e-medicapp/api/bootstrap antes de dar el acceso
por disponible, ademas del commit y del tunel registrados en deployment.json.

PRIMERA INSTALACION O ACTUALIZACION EN WINDOWS
Requisitos: JDK 25, Node.js 24, PostgreSQL 17 o superior y cloudflared.
Esta PC utiliza PostgreSQL 17.5 y Node.js 24.18.0; el JDK 25 se conserva portable
en .tools/java/. No se modifica el Java predeterminado de otros proyectos.
Los scripts detectan las herramientas instaladas y un JDK portable bajo .tools/.
Si hace falta indicar rutas, usar EMEDICAPP_JAVA_HOME, EMEDICAPP_NODE_HOME,
EMEDICAPP_PG_BIN y EMEDICAPP_CLOUDFLARED en el entorno de Windows.
Los accesos y las verificaciones usan la configuracion EMEDICAPP_* del proyecto.
Suspenden los parametros genericos Spring/Server/JVM heredados de otros proyectos
durante el inicio y restauran el entorno del lanzador al terminar. No cambian
la configuracion permanente de Windows.
Para cloudflared: winget install --id Cloudflare.cloudflared --exact

Si no existe el JAR, AbrirDemoPages.cmd lo compila automaticamente. La primera
compilacion requiere Internet para dependencias. Despues de cambiar el codigo:
  1. DetenerDemoPages.cmd
  2. powershell -NoProfile -ExecutionPolicy Bypass -File scripts\Build.ps1
  3. AbrirDemoPages.cmd
Tambien se puede ejecutar scripts\Start-DemoPages.ps1 -Build -OpenBrowser con la
demo detenida. No reemplazar el JAR mientras esta abierto por Java.

El acceso no adopta ni termina procesos ajenos. Si 8082 esta ocupado por el DEMO
local iniciado con AbrirDemo.cmd, cerrarlo antes con scripts\Stop.ps1 -Environment
Demo. El arranque de Pages configura exclusivamente su propio backend DEMO.

DATOS Y SESIONES
PostgreSQL escucha solo en 127.0.0.1. Los binarios deben coincidir con la version
principal del cluster que ya exista. .runtime/local-db.json conserva el puerto y
una contrasena aleatoria protegida mediante DPAPI para el usuario de Windows.
No borrar .runtime: contiene los datos, documentos, credenciales locales y logs.
El tunel publica el backend; GitHub Pages conserva solo los archivos de la web.

El backend admite https://scalaris.com.ar y https://jereprograma.github.io,
ademas de https://localhost para el cliente Android.
La sesion entre dominios se conserva por pestana mediante X-Auth-Session y
mantiene validacion CSRF. No depende de habilitar cookies de terceros.
El proxy del mismo dominio tambien usa estas sesiones aisladas: nunca mezcla
cookies del sitio corporativo con las cuentas de E-MEDICAPP.
La sesion vence a los 30 minutos de inactividad o al reiniciar Java; el navegador
solicita ingresar nuevamente. El correo tipeado en el ingreso no se borra al
cambiar de ventana o minimizar. La contrasena no se guarda en localStorage.

Para restaurar datos de presentacion con respaldo previo y sin borrar lo anterior:
  powershell -NoProfile -ExecutionPolicy Bypass -File scripts\ResetDemo.ps1 -NoStart
Ejecutar solo con la demo de Pages detenida. Luego abrir AbrirDemoPages.cmd.
El guion de presentacion recomienda crear una compra sencilla con retiro y luego
mostrar entrega, pagos, factura y cierre mediante las cuentas de cada rol.

DIAGNOSTICO
.runtime/demo-pages.json: estado, backend HTTPS y enlace de Scalaris para compartir.
.runtime/demo-tunnel.stderr.log: conexion saliente de Cloudflare.
.runtime/app-Demo.stdout.log y .stderr.log: inicio del backend.
.runtime/postgres.log: base local.
El acceso informa disponibilidad solamente despues de comprobar modo DEMO por
HTTPS y el permiso CORS para el frontend publico. La verificacion del frontend publico
se completa en GitHub Actions; el tunel por si solo no publica el frontend.

El mecanismo anterior de ngrok y MANUAL queda en scripts/Start-Public.ps1,
Configure-Public.ps1 y Stop-Public.ps1 como alternativa historica. Su configuracion
privada no se usa para el nuevo DEMO de Pages.
